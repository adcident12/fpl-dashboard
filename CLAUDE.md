# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local FPL (Fantasy Premier League) decision-support dashboard. It reads only the public, unauthenticated FPL API — there is no login and no team automation. The user makes actual squad changes on the official FPL site themselves; this app just helps them decide what to do (player stats, fixture difficulty, squad view, transfer/captain suggestions).

The full spec lives in [.github/prompts/fpl-dashboard.prompt.md](.github/prompts/fpl-dashboard.prompt.md), written as 4 build phases (player table → fixture grid → my squad → transfer/captain suggestions). All 4 phases are implemented.

## Commands

Run from the repo root (`package.json` orchestrates both workspaces):

- `npm run install:all` — install server and client dependencies (they are separate npm packages, not a workspace/monorepo).
- `npm run dev` — run server (port 3001) and client (Vite dev server, port 5173) concurrently, with hot reload.
- `npm run build` — build the client only (`client/dist`).
- `npm start` — start the server only; if `client/dist` exists, the server serves it directly (single-process production mode).

There is no test suite and no linter configured in this repo.

To run just one side: `npm --prefix server start` or `npm --prefix client run dev`.

**Split deployment (GitHub Pages + Render):** GitHub Pages only serves static files, so `client/` and `server/` deploy separately — see `.github/workflows/deploy-pages.yml` and `render.yaml`. This is a second deployment mode alongside the single-process one above, not a replacement: `client/vite.config.js`'s `base` only switches to `/fpl-dashboard/` when the workflow sets `GITHUB_PAGES=true`, and `client/src/api.js`'s `API` constant only points at a remote backend when `VITE_API_BASE` is set at build time — both default to the original root-relative behavior otherwise, so `npm run build && npm start` locally is unaffected. Full setup steps (Render's free-tier cold-start/cache caveats included) are in the project's Obsidian doc, not duplicated here.

## Architecture

**Two independent npm packages, no shared code:**
- `server/` — Node.js (ESM) + Express. Fetches FPL API data, transforms/joins it, and serves JSON at `/api/*`.
- `client/` — React + Vite. Fetches from `/api/*` (proxied to `localhost:3001` in dev via `vite.config.js`).

**Server data flow (`server/fpl.js`):**
1. `getBootstrap()` / `getFixtures()` / `getElementSummary()` / `getEntryPicks()` / `getEventLive()` / `getEntryHistory()` — raw, disk-cached fetches from `https://fantasy.premierleague.com/api/*` (5 min TTL, see `server/cache.js`, backed by JSON files in `server/.cache/`).
2. `buildData()` — the core transform: joins `bootstrap-static` elements + teams + fixtures into a flat `players` array with computed fields (price in £m, parsed numeric strings, next-3-fixtures with FDR, differential). Nearly every other function builds on this. Every fixture object (here, `buildFixtureGrid()`'s cells, and `getSquadContext()`'s `eventFixturesByTeam`) also carries `kickoffTime` — raw `kickoff_time` from the FPL API (ISO 8601 UTC, `null` when FPL hasn't confirmed a time yet, e.g. a gameweek far enough out or a fixture awaiting rescheduling) passed through unformatted; the client (`FdrBadges.jsx`'s `formatKickoff()`/`formatKickoffShort()`) converts to the viewer's own local time via `Date`/`toLocaleString()` with no explicit locale/timeZone argument, so a fan actually knows when to tune in rather than reading a raw UTC timestamp. Its `meta` also carries `dataFetchedAt`/`dataTtlMs` (via `cache.js`'s `getCacheMeta()`, which reads a cache file's timestamp without affecting `getCached()`'s own fresh/stale logic) — the older of the `bootstrap`/`fixtures` cache timestamps, so the client can show a live "Updated Xm ago" indicator (`App.jsx`, header, ticks every 30s). `meta.nextDeadline` (`{ eventId, eventName, deadlineTime, deadlineEpochMs }`) is the next gameweek deadline that hasn't passed yet — found by scanning `bootstrap.events` for the first `deadline_time` after "now" directly, rather than trusting the `is_next` flag, which can lag right around a deadline; the header renders it as a live countdown (same 30s tick as freshness) that turns amber under 24h and red under 3h.
3. `buildFixtureGrid()` — teams × next-5-gameweeks matrix for the fixture difficulty view. Each cell is an **array** of fixtures, not a single fixture-or-null — 0 fixtures means a Blank Gameweek (BGW), 2+ means a Double Gameweek (DGW), both real occurrences during a season when the schedule reshuffles postponed matches. It also returns `doubles`/`blanks` summary arrays (`{ teamId, teamShort, event, count? }`) computed in the same pass, which the client (`FixtureGrid.jsx`) renders as a banner above the grid grouped by gameweek.
4. `buildSquad(teamId, eventId)` — joins a user's picks (`entry/{id}/event/{gw}/picks`, plus `event/{gw}/live/` for each pick's live points) against `buildData()`'s player list. Starting XI vs bench is derived from `pick.position <= 11` — the picks API has no `starting` boolean.
5. `buildTransferSuggestions()` / `buildCaptainSuggestions()` / `buildSquadScan()` — the scoring engine (see below), built on `getSquadContext()` which combines squad picks + bank (read directly from `entry_history.bank`, not derived) + the full player pool, **plus `eventFixturesByTeam`**: every team's actual fixture(s) for the specific gameweek being planned for (`ctx.ev`), read straight from `getFixtures()` rather than from `buildData()`'s `nextFixtures` (which lists the next 3 *real matches* chronologically and so silently skips a Blank Gameweek, and can't tell a Double Gameweek's two legs apart from two fixtures spread across different future gameweeks). `eventFixturesFor(ctx, teamId)` reads it — 0 entries = blank, 2 = double — and both `scoreTransferComponents()` and `buildCaptainSuggestions()` use it to correct the score: a blank forces the fixture component to **0** (not the neutral-midpoint fallback used for genuinely missing data — a blank is a guaranteed zero, not an unknown), a double adds `SCORING.dgwBonus` (+20) for the extra scoring chance. Every scored player/candidate carries `eventFixtureCount`/`blankEvent`/`dgwEvent`, and `breakdown.fixture.note` (`'blank'`/`'double'`/`null`) says which adjustment fired — surfaced in the UI as a BLANK/DGW×2 badge next to the name (`SuggestionsView.jsx`'s `EventFlagBadge`) so the adjustment is never a silent number shift. `buildSquadScan()` runs the same per-player logic as `buildTransferSuggestions()` (factored into `scoreAffordableCandidates()`/`scoreTransferComponents()`) across all 11 starting players at once, comparing each to its top same-position replacement — one swap at a time, not a combined-budget multi-swap optimization.
6. `buildBonusPredictor(eventId)` — fan feature, league-wide (no team ID needed): projects live bonus points (3/2/1) per fixture from each player's current `bps` (Bonus Points System score, from `event/{gw}/live/`), using `computeBonusPoints()` — FPL's own tie-break rule (rank by BPS descending, group players tied on the exact value, award the group's *starting* rank's points to every member, then advance the running rank by the group's size, not by 1 — reproduces FPL's real "2 tied for 1st both get 3, next distinct player gets 1, '2nd' is skipped" behavior). Grouped per fixture (each player's fixture read from `explain[0].fixture`, not assumed from their team's single fixture that event) so bonus is never compared across different matches; only fixtures with `started === true` are included. Uses a 60-second cache (`LIVE_BONUS_TTL_MS`, passed as `getEventLive(eventId, ttlMs)`'s 2nd arg) instead of the app-wide 5 minutes, since BPS changes minute to minute during play — `getCached()`'s TTL is a per-call read-time check against the cache file's own timestamp, not something stored with the file, so this doesn't affect `buildSquad()`'s own (default-TTL) reads of the same cached data. A fixture's `finished` flag is `f.finished || f.finished_provisional` (same quirk as `buildFixtureGrid()`'s `done`) — a fully-played match can sit at `finished=false` for up to ~1h while FPL's own bonus confirmation catches up, and `finished_provisional` (plus the score already being posted) is the earlier, reliable signal that the match is actually over and `confirmedBonus` (`stats.bonus`) is authoritative.
7. `buildChipPlan(teamId, eventId)` — chip planning helper. `bootstrap.chips[]` (8 entries: 4 chip types × 2 season halves, each `{ name, start_event, stop_event }`) is the **authoritative source for chip windows** — never hardcode the GW19 half-boundary, read it from here. `entry/{id}/history/`'s own `chips[]` (`{ name, event, time }`) is the user's actual usage, matched to a window by `name` + `event` falling inside that window's range — so, unlike the original feature-roadmap note assumed, **no manual "which chips have I used" input is needed**. Each returned window carries a single `status` (`used`/`available`/`expiringSoon`/`upcoming`/`expired`) the client switches on directly. `recommendations[]` are heuristic, one per chip type, only computed when that chip is currently available: Bench Boost when all 4 bench players have an easy next fixture and are expected to play; Triple Captain when the top captain-formula pick also has an easy next fixture; Free Hit when 2+ of the user's own squad's teams have a blank in the very next gameweek (reuses `buildFixtureGrid()`'s `blanks`); Wildcard when 4+ starting XI are flagged `upgrade` by `buildSquadScan()` (squad needs a broad rebuild, not a single swap).

Routes in `server/index.js` are thin wrappers around these functions; there's no separate route/controller/model layering.

**OpenAPI/Swagger (`server/openapi.js`):** a hand-written OpenAPI 3.0 document (validated with `@apidevtools/swagger-parser`, not just "renders in Swagger UI without erroring") covering all 16 routes — **not** generated from JSDoc comments on the routes themselves (`swagger-jsdoc`), because this API's response shapes are deeply nested and quirky enough that inline comment blocks would drift silently; the schemas here are typed from the same verified field knowledge as `fpl-api-quirks.instructions.md`/`fpl-scoring.instructions.md`. Served at `/api-docs` (Swagger UI) and `/api-docs.json` (raw spec — CORS is already open, so external tooling can fetch it directly; built specifically so an OpenAPI→MCP bridge can consume it). **When a route's request/response shape changes, update the matching schema in `openapi.js` in the same commit** — same discipline as the API quirks doc, and worth being strict about here since a wrong schema silently breaks whatever consumes the spec, not just a doc reader.

**Client structure (`client/src`):** `App.jsx` owns the player table + tab navigation and fetches via `api.js`; `FixtureGrid.jsx`, `SquadView.jsx`, `SuggestionsView.jsx`, `ChipsView.jsx`, `BonusView.jsx`, `RivalryView.jsx`, `SetPiecesView.jsx`, `DreamTeamView.jsx`, `GuideView.jsx` are the other nine tabs, each fetching its own data independently (no global state/store, except language — see below). `ChipsView.jsx` renders `buildChipPlan()`'s 8 windows as two half-of-season columns of status cards (color/label driven by each window's `status`) plus a recommendations list; like `SquadView`/`SuggestionsView` it needs a Team ID, so it reuses `useTeamId()`/`TeamIdInput`/`TeamIdEmptyState`. `FixtureGrid.jsx` also renders a "Fixture Swing" ranking above the grid — teams sorted by average FDR across the same visible gameweek window, easiest run first — computed entirely client-side (`computeFixtureSwing()`) from the grid's own already-fetched data, not a new server endpoint: it flattens each team's per-gameweek fixture arrays (so a Blank Gameweek contributes nothing to the average instead of skewing it, and a Double Gameweek's two legs both count), and reuses `FdrBadges.jsx` for the mini fixture-badge row per team since the flattened shape already matches what that component expects. The top/bottom 3 rows get their rank number colored green/red (`swingRankClass()`, same `--color-easy`/`--color-hard` tokens as the FDR badges) so "easiest run" / "hardest run" reads at a glance — a full-row `border-l` accent was tried first and dropped after user feedback that it read as too loud/heavy next to the meter bar's own per-row coloring; coloring just the rank number is a lighter touch that doesn't compete with it. Computed from each team's fixed `rank` (canonical easiest-first order, attached once in `computeFixtureSwing()`) rather than its current display position, so the highlight never moves when the row order below is reversed; each row is a `max-sm:flex-col` stack (rank+avatar+name+meter+avg on one line, badges indented below) rather than a single wrapping flex row, since letting badges wrap freely alongside the name/avg text was found to overflow unpredictably on narrow screens depending on team-name length. Redesigned after checking how real FPL fixture-ticker tools (Fantasy Football Scout, Fantasy Football Pundit) present this same idea — aligned columns, a numeric difficulty score, and a compact color-coded visual next to it, all sortable: each row now gets a small team-color avatar chip (`teamColor()`, imported from `PitchView.jsx`) for visual identity in place of no-crest-assets plain text, a `DifficultyMeter` fill-bar bucketed into the same easy/med/hard tones as `FdrBadges` (not a 5-stop gradient, to keep one shared color vocabulary app-wide) sized by `(5-avgFDR)/4` — its fill color is looked up from `METER_FILL_CLASS = { easy: 'bg-easy', med: 'bg-med', hard: 'bg-hard' }`, **not** a `` `bg-${bucket}` `` template string: a first version used the template form and shipped with every medium-difficulty bar (`fdrBucket` → `'med'`) invisible, because Tailwind's compiler only generates CSS for complete class-name strings it can find in the source, and `bg-med` never appeared literally anywhere else in the codebase (unlike `bg-easy`/`bg-hard`, which happened to already exist from the sort-toggle buttons right below it and so "worked" by accident) — the exact `pos-${positionId}`-style trap this file's own Tailwind-exemption list already warns about, missed here because the accidental partial success masked it until a user reported the bars showing no color, and an "Easiest first"/"Hardest first" pill toggle (`sortDir` state, reverses display order only — `rank`/accent stay anchored to the canonical order as above). `RivalryView.jsx` is a head-to-head comparison between two squads — reuses `/api/squad` twice (once per side) rather than a new server endpoint, matching the project's existing "thin server, computed client-side" precedent (e.g. `PitchView`'s current-vs-suggested toggle, or Fixture Swing above). Side A defaults to the same shared `fpl-team-id` localStorage key every other tab reads (`useTeamId()`'s default), so "your team" prefills automatically; Side B uses a second, distinct key (`useTeamId('fpl-rival-team-id')`, via `useTeamId()`'s optional `key` param) so the two slots don't clobber each other. Renders both squads side by side with `PitchView` and a plain-language "banter" line generated from the two teams' `teamPoints` difference this gameweek (tie / close / win / blowout thresholds) — no server involvement, just a friendly read of two already-fetched responses. The banter line comes from `BANTER_PHRASES`, a curated bank of 6 hand-written lines per outcome category per language (EN/TH), **not** a live AI/API call — that was considered and deliberately skipped: this app has never held a server-side secret (see "What this is" above — public FPL API only), a per-view LLM call would need one plus add real latency/cost/failure modes to an otherwise instant, free page, and a hand-picked bank gives more consistent comedic quality than a live generation call would per-request anyway. `pickBanter()` selects deterministically (`hashSeed()` over `teamIdA-teamIdB-pointsA-pointsB`, not `Math.random()`) so the same matchup at the same score always shows the same line — re-renders don't make it flicker — while a different matchup or a different gameweek's score picks a fresh one from the pool. `BanterCard` adds two more things on top of the phrase itself: a copy-to-clipboard button (`navigator.clipboard.writeText`, Wordle-share-button-style — brief icon swap to a checkmark instead of a text change, silently no-ops on failure since a failed copy of a nice-to-have line isn't worth surfacing as an error) and a category-specific CSS entrance animation (`.banter-tie/close/win/blowout` in `styles.css` — a blowout gets a scale-bounce with a gold glow, a close game gets a nervous wiggle, distinct enough that the motion itself telegraphs the result before you've read the words) — respects the app-wide `prefers-reduced-motion: reduce` override automatically, and replays on every new phrase because the caller keys `<BanterCard>` by the phrase text itself, forcing React to mount a fresh DOM node rather than patch the existing one in place. A `mode` toggle (`'managers'` default, or `'clubs'`) switches the whole tab between that manager-vs-manager view and `ClubH2H` — a second, independent head-to-head between two **clubs** the user picks directly (not derived from anyone's squad), sourced from `/api/teams` + `/api/fixtures` (both already existed; this is a pure client-side filter, the same "thin server" precedent as everything else on this tab) rather than a new server endpoint. `clubMeetings()` filters the season's full raw fixture list down to the (usually 2 — home leg + away leg, but computed generically rather than assumed) meetings between the two chosen club IDs, and `seriesRecord()` tallies wins/draws from only the ones that have actually finished (an upcoming or in-progress leg has no score to judge yet, so it's excluded rather than counted as a placeholder draw). Each meeting is a `MeetingCard` — club avatars (`teamColor()`, the same hash `PitchView.jsx`'s jerseys and Fixture Swing's rows use, for one consistent color per club everywhere in the app), the score once finished or the kickoff time (`formatKickoff()`) while still upcoming, and each side's FDR for that specific match (`fdrBucket()`/`.fdr-badge`, reused directly rather than through `FdrBadges.jsx` itself since that component's shape is "one player's several upcoming fixtures," not "one match's two sides"). A meeting kicking off today also gets the same `.matchday` border-beam treatment as the Fixtures grid and FDR badges — which is what prompted refactoring `.matchday` from a `.cell`-only rule into a generic one (`styles.css`): a third near-identical block for meeting cards would have been the same mistake `bg-${bucket}` already was elsewhere, one more copy to drift out of sync instead of one shared mechanism three call sites opt into. `SetPiecesView.jsx` groups every player with a non-null `penaltyOrder`/`freeKickOrder`/`cornerOrder` by team into 3 ranked lists per club — computed entirely client-side from the already-existing `/players` payload (`freeKickOrder`/`cornerOrder` added to `buildData()`'s player mapping alongside the pre-existing `penaltyOrder`, from `direct_freekicks_order`/`corners_and_indirect_freekicks_order`), no new server endpoint. Informational only, same reasoning as the penalty badge (`fpl-scoring.instructions.md`): too unpredictable to weight into any score. Names wrap (`break-words`, no `truncate`) rather than ellipsis-and-hope — an earlier version truncated to fit 3 columns in a card and relied on a hover `Tooltip` to reveal the rest, which meant a name like "Gyökeres" was unreadable at a glance on both desktop and touch; wrapping plus a wider card `minmax` (300px, was 260px) fits full names directly, and each list's `order === 1` entry is picked out in accent/bold since "who's first choice" is the one fact worth scanning for, not "who's 4th in line". `DreamTeamView.jsx` renders `buildDreamTeam()`'s 11 players via `PitchView` (reused as-is — no bench, so `PitchView` just never renders a bench section) plus a below-pitch list ranked by points and a "Star of the Gameweek" callout for the top scorer (`teamColor()`, `PitchView.jsx`'s jersey-color hash, exported specifically so this callout's avatar circle matches the color that player's jersey uses on the pitch below it); deliberately does not touch `PitchView.jsx` itself (e.g. to show per-player points on the jersey chip) given that component's documented fragility history — the points ranking and star callout live in ordinary markup around the pitch instead. `BonusView.jsx` is the one tab that needs **no Team ID** (league-wide fan data, not squad-specific) — it renders `buildBonusPredictor()`'s per-fixture cards (BPS-sorted player list, gold/silver/bronze 3/2/1 bonus badges) and re-polls every 60s (`REFRESH_MS`, matching the server's own `LIVE_BONUS_TTL_MS` so a faster client poll wouldn't just re-read the same cached response) for as long as the tab stays mounted; a fixture's badge tooltip and "LIVE"/"FINAL" tag text differ depending on `finished` (projection vs FPL's own confirmed bonus); the "LIVE" tag (not "FINAL") gets a small pulsing dot (`.bonus-live-tag.live::before`, a CSS `animation`) so an in-progress fixture reads as actually moving rather than just a static label — respects the app-wide `prefers-reduced-motion: reduce` override at the top of `styles.css` (`animation: none !important`) automatically, no extra guard needed. `GuideView.jsx` is the one tab with **no data fetching at all** — a static, hand-written explainer of the scoring formula and every badge used elsewhere in the app (reusing the exact same CSS classes as live badge previews, not a text description), added because badge/score tooltips rely on `title` attributes that don't work on touch devices; its EN/TH content lives directly in the component as two JSX blocks switched on `useLang()`'s `lang`, **not** through `i18n.jsx`'s `STRINGS` dictionary — that dictionary is for short UI labels, and per-sentence keys for paragraph-length prose would be unwieldy. `PitchView.jsx` is a shared formation-view component (GK/DEF/MID/FWD rows sized to the squad's actual formation, bench below, team-colored jersey chips — no image assets) used by both `SquadView` and `SuggestionsView`'s squad-scan section; given `buildSquadScan()`'s rows, it numbers starting players flagged `upgrade` by transfer-priority (biggest score gap first). Its `mode` prop (`'current'` default, or `'suggested'`) toggles between the real squad and a hypothetical one where every `upgrade`-flagged starter is swapped for its top scan candidate (dashed-outline chips) — `SuggestionsView` exposes this as a "current team / suggested team" toggle above the pitch. `FdrBadges.jsx` is the shared fixture-difficulty badge row (opponent + color-coded FDR, used by the Players table, My Squad, Fixture Swing, and every Suggestions candidate list) — every server-side suggestion object (transfer candidates, captain candidates, squad-scan `suggestion`) carries a `nextFixtures` array in the same shape as `buildData()`'s players specifically so this one component can render all of them. It also exports `formatKickoff()`/`formatKickoffShort()` (added after a user asked to see match day/time, not just the opponent+FDR) — both take the fixture's raw `kickoffTime` (ISO UTC, possibly `null`) and format via `Date`/`toLocaleString()` with no explicit locale/timeZone, so kickoff shows in the viewer's own local time; the `Short` variant drops month/day (just weekday+time) for `FixtureGrid.jsx`'s own cramped cell face, while the full variant (weekday, day, month, time) is what every tooltip shows, including `FixtureGrid.jsx`'s own (it doesn't go through the shared `<FdrBadges>` component — its grid cells are custom-rendered — so it imports these two formatters directly rather than duplicating the logic). `FixtureGrid.jsx`'s cells show the formatted kickoff time directly on the cell face for any fixture that hasn't been played yet (`.cell-kickoff`, styled like the existing `.cell-score` it replaces once a match finishes) — the Fixtures tab is specifically where a fan browses upcoming matches, so this is the one place kickoff info is worth showing at a glance instead of only on hover/tap. A cell for a fixture kicking off **today** (`isMatchday()` — same calendar date as the viewer's local `Date.now()`, checked by year/month/date so it holds all day regardless of kickoff time, and only for a match that hasn't finished — `!f.done`) gets `.matchday`: a slowly rotating "border beam" around its perimeter (`@property --matchday-angle` interpolating a `conic-gradient`'s rotation, masked to just the border ring via `mask-composite: exclude`) so a fan's eye is drawn straight to "this one's on today" while scanning the grid, without reading every cell's kickoff time. `@property` support degrades gracefully — a browser without it just keeps the angle fixed at its initial value, leaving a static highlighted ring instead of a broken effect — and the animation itself, like every other one in the app, is silenced automatically by the `prefers-reduced-motion: reduce` override at the top of `styles.css`. `isMatchday()` itself lives in `FdrBadges.jsx` (exported, imported back into `FixtureGrid.jsx`) rather than being FixtureGrid-only, because a user asked whether the "today" treatment should also reach the FDR badges shown everywhere else a player's next fixture appears — `FdrBadges.jsx` gets the same border-beam treatment (`.fdr-badge.matchday`, a smaller `inset`/`padding` variant of the same `@property`/`conic-gradient` mechanism so the ring stays proportional to a much smaller pill), so a player whose next match is today is highlighted consistently on the Players table, My Squad, Suggestions, and Fixture Swing too — not just the Fixtures tab's own grid. `FdrBadges.jsx`'s fixture objects never carry a `done` flag the way `FixtureGrid.jsx`'s cells do, so its own `isMatchday()` check has no `&& !done` guard — unnecessary there, since every fixture that reaches this shared component is already current-gameweek-or-later by construction (`buildData()`/`getSquadContext()` never include a fully-past fixture in the first place).

**Localization (`i18n.jsx`):** EN/TH UI strings live in one `STRINGS` dictionary keyed by dotted names (e.g. `table.player`); `LangProvider` (wraps `<App>` in `main.jsx`) is the **one deliberate exception** to "no global state" — it's a React Context holding `{ lang, setLang, t }`, needed because the language toggle in `App.jsx`'s header must stay in sync across every tab, several levels deeper than prop-drilling would reach cleanly (`SuggestionsView` → `PitchView`/`FdrBadges`/`ScanRow`/`CandidateRow`). `useLang()` reads it; language persists to `localStorage` (`fpl-lang`, default `'en'`) the same way `useTeamId()` persists the team ID. **Only UI chrome is translated** — player/team/opponent names and other FPL API data are never translated, and technical fallback error strings in `api.js` (e.g. "Failed to load squad (500)") intentionally stay in English, matching how raw server error messages are already shown as pass-through text elsewhere. Adding a string: add both `en`/`th` entries to `STRINGS` in `i18n.jsx`, then reference via `t('your.key')` (or `t('your.key', { var })` for `{{var}}` interpolation).

**Styling — Tailwind CSS v4 + a slimmed-down `styles.css`, deliberately hybrid, not "all Tailwind":** `@tailwindcss/vite` is wired into `vite.config.js`; `styles.css` opens with `@import "tailwindcss";` then an `@theme` block mapping the app's design tokens (`--color-bg/panel/panel-2/panel-3/text/muted/line/accent/accent-2/easy/med/hard`, `--radius-sm/md/lg/xl`, `--font-display`/`--font-body`) into Tailwind's namespace, so `bg-panel`, `text-accent`, `rounded-md`, `font-display` etc. all resolve to *this app's* values, not Tailwind's defaults. `--transition: 200ms cubic-bezier(0.2, 0, 0, 1)` (Material 3's "emphasized" easing) stays a plain custom property (referenced by the hand-written CSS below; Tailwind has no matching utility). `--font-display` is Rajdhani, loaded via Google Fonts in `index.html`, used only for headings/tabs/section labels — data-dense tables stay on `--font-body` for legibility.

**Visual language — Material Design 3, dark theme (2026-09-05 redesign):** the `--radius-*` scale and `--color-panel-3` (a third, lighter surface tone — MD3's "surface-container-highest") exist specifically to support this. Cards/panels/tables get `shadow-sm` (Tailwind's default shadow scale, used as-is — no custom elevation tokens; it's dark-theme-appropriate without tuning) via className, not the hand-written classes, wherever the surface is one already styled with Tailwind utilities; **filled buttons are pill-shaped** (`rounded-full` + `shadow-sm`, brightening/`shadow-md` on hover) and **outlined buttons stay flat** (no shadow) — this mirrors MD3's Filled vs Outlined button elevation rule. Small status badges/chips (`.pos`, `.fdr-badge`, `.badge`) are pill-shaped (`border-radius: 9999px`); breakdown chips (`.chip` in `SuggestionsView.jsx`) use `--radius-sm` (8px, MD3's chip corner radius) and `--color-panel-3` so they read as one tone lighter than the `.breakdown-row` they sit on, not blended into it. **`PitchView.jsx`'s `.jersey` uses `filter: drop-shadow(...)`, never `box-shadow`** — `box-shadow` follows an element's rectangular box, not its `clip-path`-cut silhouette, so it would draw a shadow rectangle around the jersey's invisible bounding box instead of hugging its shape; `filter: drop-shadow()` operates on the actual rendered (clipped) pixels and is the only shadow safe to use there.

**Tooltips (`Tooltip.jsx`):** replaces `title=` attributes app-wide (badges, breakdown chips, FDR badges, captain/vice-captain/news flags, the header's deadline/freshness indicators, `FixtureGrid.jsx`'s cells) because `title=` never fires on tap on a touch device — there is no hover on a phone, so every one of these was previously invisible to mobile users (the Guide tab's badge glossary was a first, page-level fix for this same gap; `Tooltip.jsx` is the per-badge fix). Hover+focus opens it on desktop; a single tap toggles it on a touch device (detected once, globally, via a one-time `touchstart` listener). Positioned with `@floating-ui/dom` (`computePosition`/`autoUpdate`/`offset`/`flip`/`shift`) and rendered through a `createPortal` into `document.body` with `position: fixed` — **not** positioned inline where the trigger sits — so it can never be clipped by an ancestor's `overflow: auto` (several triggers live inside a `.table-wrap` scroll container; an inline-positioned tooltip would get cut off there the same way a badge inside `PitchView`'s clip-path jersey used to before that was fixed), and so its look (Material-styled: rounded, bordered, themed) is fully controllable — unlike a native browser tooltip, which ignores CSS entirely and is positioned by the browser/OS, not the page (a real, user-reported inconsistency next to every other tooltip in the app once `FixtureGrid.jsx` was the one place still on native `title=`). Visual style is MD3's "plain tooltip" (small, no arrow — arrows are only on MD3 "rich" tooltips). `Tooltip`'s `as` prop (`'span'` default, `'div'` for `FixtureGrid.jsx`) picks the trigger wrapper's tag so a block-level trigger (`.cell`, a flex container) doesn't end up nested inside an inline `<span>`. **One deliberate exception kept on native `title=`:** `TeamIdControls.jsx`'s "Try sample team" button (wrapping an actionable button in `Tooltip`'s tap-to-toggle handler would fire both the tooltip toggle and the button's own `onClick` on the same tap — a real conflict, not just a missed nice-to-have, so the button's own visible label carries the affordance instead). `PitchView.jsx`'s jersey badges (captain/vice-captain/priority/news-flag) were the last other holdout, kept on native `title=` out of caution that `Tooltip`'s wrapper might interfere with `.jersey-badge`/`.priority-badge`'s `position: absolute` resolving against `.jersey-chip`'s `position: relative` — switched over after a user screenshot showed the same native-tooltip inconsistency `FixtureGrid.jsx` already had (a plain unstyled browser tooltip, and in the reported case, one that rendered floating away from the badge rather than pointing at it). The positioning worry turned out to be unfounded: `Tooltip`'s `className` prop lands on its own single `Trigger` element, not an extra wrapper around the badge, so passing the badge's existing classes there (`<Tooltip className="badge cap jersey-badge">C</Tooltip>`) keeps it a single element in exactly the same DOM position as the old `title=` span — verified with real hover screenshots on the captain/priority/news badges (correctly positioned Material tooltips, no jersey layout regression) rather than reasoned about and left unverified.

**Loading states (`LoadingSpinner.jsx`):** every "nothing to show yet" screen (initial load in `App`/`FixtureGrid`/`SquadView`/`SuggestionsView`, the Quick Squad Scan and Captain sections while scoring) uses the same `LoadingState` (centered ring spinner + label) or bare `Spinner` (dropped into a loading button, e.g. `TeamIdInput`'s Load button) — both are Tailwind's own `animate-spin` under `motion-safe:`, no custom CSS/keyframes. Before this, `SquadView` and `SuggestionsView`'s initial team load showed nothing at all while waiting (not just plain text) — a real gap, not merely unstyled. When adding a new loading state, reach for one of these two instead of ad hoc text so every wait in the app reads the same way.

Most components (`App.jsx`, `TeamIdControls.jsx`, `SquadView.jsx`, `SuggestionsView.jsx`) are styled with Tailwind utility classes directly in JSX, including responsive variants (`max-sm:`, `max-[900px]:` — Tailwind's `sm` breakpoint is exactly 640px, which is why this app's two breakpoints line up with `sm`/a custom `900px` value). **What deliberately stays as hand-written CSS in `styles.css`, and why:**
- **Classes built from a runtime value** (`` `pos-${positionId}` ``, `` `fdr-${bucket}` ``, `` `badge verdict-${verdict}` ``, `` `jersey-chip${isSuggested ? ' suggested' : ''}` ``, `` `chip-status-${w.status}` `` in `ChipsView.jsx`): Tailwind's compiler statically scans source files for complete class-name strings — it cannot see `pos-${positionId}` and so cannot generate CSS for it. These variant/color-coding families (`.pos-1..4`, `.fdr-easy/med/hard`, `.badge.verdict-*`, `.top-pick`, `.bench`, `.chip-status-*`) are small hand-written classes for exactly this reason, matched in JSX via the same template-literal pattern.
- **The responsive card-table technique** (`table.players` and its variants across Players/My Squad/Suggestions — see below): the `data-label` + `::before { content: attr(data-label) }` mechanism, `<thead>`-hiding, and the dynamic `.name:not([data-label])` title rule are structural CSS that doesn't map cleanly to inline utilities and is shared identically across four different tables.
- **`PitchView.jsx`'s jersey/pitch mechanics**: the jersey silhouette (`clip-path: polygon(...)`), the pitch gradient, and the badge-positioning fix (badges must be siblings of `.jersey`, not children, because `clip-path` clips descendants — see the comment in `PitchView.jsx`) are effect-heavy and already fragile (two real bugs were found and fixed here); the structural mechanics stay untouched on that history alone — a `chrome-devtools-mcp` browser became available partway through this project (2026-09-05) and confirmed the jersey rendering is correct as of the Material redesign, but that doesn't retroactively make restructuring this area risk-free, so the same caution still applies to *changes*, just no longer to *verification*.
- **`FixtureGrid.jsx`** (the teams×gameweeks matrix) is exempt from the whole Tailwind pass for the same reason it's exempt from the card-table treatment (see Responsive below) — kept as-is.
- Team-color hashing (`teamColor()` in `PitchView.jsx`) sets an inline `style`, not a class, so it was never a Tailwind concern.

When adding new UI: reach for Tailwind utilities first; only add a hand-written class in `styles.css` if it needs a runtime-constructed class name, overrides native-control pseudo-elements (like the custom `<select>` arrow or the checkbox-as-toggle-switch — both still hand-written for exactly this reason), or is part of the card-table/jersey systems above.

**Responsive:** two breakpoints at the end of `styles.css`, `900px` (tightens spacing, shrinks `PitchView` jersey chips) and `640px` (stacks every control bar full-width, shrinks the pitch further, and turns every `table.players`-based table — Players/My Squad/Suggestions — into one card per row via a CSS-only technique: `<thead>` hidden, each `<td>` becomes a flex row labeled by its `data-label` attribute's `::before` content, and `td.name:not([data-label])` renders as the card's title instead of a labeled field). Every `<td>` that needs a mobile label carries `data-label={t('...')}` in the JSX — a `<td>` with no `data-label` and no `.name` class (e.g. `colspan` divider/breakdown rows) just renders as a plain block. **`table.fixture-grid` (FixtureGrid.jsx) is deliberately exempt** from the card treatment — it's a teams×gameweeks matrix, not a list of records, and stacking it would defeat comparing several gameweeks side by side; it only scrolls horizontally with tighter cell sizing at 640px. Every `table.players`-based table's wrapper div also carries `max-h-[72vh] overflow-auto max-sm:max-h-none max-sm:overflow-visible` (App.jsx, SquadView.jsx, SuggestionsView.jsx ×3): on desktop the bounded, independently-scrolling panel is a deliberate spreadsheet-style pattern (filters/header stay put while results scroll); on mobile it was a real UX bug found during a full-app review — a second, nested scroll region trapped inside 72% of the viewport height reads as broken on a phone (where the whole point of the card-per-row layout is a single continuous feed, the way any normal mobile list scrolls), not as a deliberate desktop affordance. `max-sm:` strips the height cap and lets the cards flow as part of the page's own scroll instead.

**Mobile primary navigation — fixed bottom tab bar (2026-09-05, Facebook-mobile-style):** `App.jsx`'s top pill nav (`hidden sm:inline-flex` — visible ≥640px) and a second `<nav>` right below the header (`hidden max-sm:flex fixed bottom-0 inset-x-0` — visible <640px only) render the *same* `TABS` array, so there's exactly one source of truth for the tab list; both read/write the same `tab` state, so switching via either stays in sync. This exists because the original single top nav had **no width constraint of its own** — the tab buttons in one `inline-flex` row just grew the whole page wider than the viewport on a phone instead of wrapping, silently making some tabs unreachable; this was found (and the whole redesign visually verified, screenshot by screenshot, for the first time this session) once real browser tooling became available, not by inspecting the CSS. The top pill nav (`sm:` and up) got a second, related bug once the tab count grew from 6 to 9 (the 5 fan features): still no overflow at the ≥640px widths it targets, but at tablet widths (~640-900px) it no longer fit on one line, and without `flex-wrap` each button's flex item shrank narrower than its own label instead of the row wrapping — squeezing "MY SQUAD"/"SET PIECES"/"DREAM TEAM" onto 2 lines inside their own pills while the nav as a whole still overflowed the header. Fixed the same way as any pill-group that can outgrow its row: `flex-wrap` on the `<nav>` (wraps onto a 2nd line instead of shrinking or overflowing) plus `whitespace-nowrap` on each button (keeps each label on one line while its container wraps around it) — verified with real screenshots at 640/700/1200px, not just at the two nominal breakpoints. The bottom bar itself got the same "9 tabs is a lot" problem the top pill nav did, in its own way: it originally split evenly (`flex-1` per button) across the screen width, which at 9 tabs squeezed every icon+label into too little space to feel comfortable — a real user complaint ("เบียดกัน", crowded), not a hypothetical one. Fixed by making the bar horizontally scrollable instead of forcing everything to fit: each button is `shrink-0 min-w-[64px]` (a fixed, comfortable size) and the `<nav>` itself is `overflow-x-auto` with the `.no-scrollbar` utility (`styles.css`) hiding the scrollbar chrome. This is also the "add swipe" half of the same request — a horizontally-scrollable element already responds to touch swipe natively, so no gesture library was added; the ask was satisfied by the same fix as the crowding, not a separate feature. `bottomNavRefs` (a `Map` of tab key → button DOM node, populated via each button's `ref` callback) backs a `useEffect` that calls `scrollIntoView({ inline: 'center' })` on the active tab's button whenever `tab` changes, so switching tabs from the top nav (desktop/tablet) or reloading onto a tab scrolled out of view both keep the bottom bar's highlighted tab actually visible instead of leaving the user to discover the scroll themselves. `Icons.jsx` has one small hand-drawn line-icon SVG per tab (no icon library — a handful of glyphs isn't worth the dependency) rendered at `w-5 h-5` in the bar, colored via `currentColor` so the active/inactive text-color classes drive the icon too. The bottom bar has `style={{ paddingBottom: 'env(safe-area-inset-bottom)' }}` for notched phones, and the app's outer wrapper gets `max-sm:pb-20` so the bar never permanently covers the last bit of page content (it still covers content transiently while scrolling past that screen position, same as any fixed bottom bar — Instagram/Facebook do this too, it's not a bug). The header's own mobile row had a second real bug found the same way: the deadline badge had no `whitespace-nowrap`, so on a narrow screen its own text wrapped to two lines inside the pill and visually broke apart — every header pill/button now carries `whitespace-nowrap` for exactly this reason, and the verbose "Gameweek 3 · 652 players" text hides on mobile (`max-sm:hidden`) in favor of just the freshness dot + deadline badge, decluttering the top bar the way a minimal mobile app header does.

## FPL API field quirks — read before touching data mapping

The public FPL API is undocumented and has non-obvious field names/shapes. **Full verified mapping: [.github/instructions/fpl-api-quirks.instructions.md](.github/instructions/fpl-api-quirks.instructions.md).** Do not guess field names — check that file first, and add any newly-discovered quirk to it. Key traps:

- Players are under `elements`, not `players`.
- `element_type` is a position **ID** (1=GK, 2=DEF, 3=MID, 4=FWD), not a string — map via `element_types`.
- `now_cost` is in tenths of £m (`60` = £6.0m).
- Many stats (`form`, `selected_by_percent`, `value_season`, `ict_index`, `expected_goals`, etc.) are **strings**, not numbers — must be parsed.
- FDR is per-team-per-fixture: `team_h_difficulty` / `team_a_difficulty` (1-5 scale, 1=easiest), not a single `difficulty` field.

## Scoring engine

Transfer and captain suggestions use one transparent, reproducible formula — **never a black-box ranking; always return the per-component breakdown** (raw value, normalized 0-100 value, weight, weighted points). Full spec: [.github/instructions/fpl-scoring.instructions.md](.github/instructions/fpl-scoring.instructions.md).

- All weights live in the single `SCORING` config object in [server/fpl.js](server/fpl.js) — tune there, not inline.
- Every component is normalized to 0-100 before weighting; a missing/null component falls back to the neutral midpoint (50), never to zero — **except the fixture component on a confirmed Blank Gameweek**, which is forced to 0 (see below): that's a known guaranteed zero, not missing data, so the neutral-midpoint fallback would be wrong there.
- FDR normalization is `(5 - avgFDR) / 4 * 100` (1=easiest→100, 5=hardest→0). Note the code comment in `fpl.js` explaining why this differs from the prompt file's original (buggy) `(6 - avgFDR)/4*100` formula — the `(5 - x)/4` form is the corrected, actually-0-100-bounded version.
- Transfer scoring weights next-3-gameweek average FDR; captain scoring weights the actual fixture(s) of the specific gameweek being planned for (not "whichever real match comes next chronologically" — see `buildCaptainSuggestions()` above) and only considers the starting XI.
- **Double/Blank Gameweek correction**: both transfer and captain scoring adjust the fixture component using `eventFixturesFor(ctx, teamId)`'s count for the target gameweek — 0 forces it to 0, 2+ adds `SCORING.dgwBonus`. This is layered on top of the normal FDR normalization above, not a replacement for it.
- **4th component — `underlying` (xG+xA per 90, `normUnderlying()`)**: added alongside form/fixture/value (weights rebalanced — see `SCORING`) because `form` is backward-looking actual points (mixed with finishing luck) while xGI is forward-looking "should be scoring this much"; kept as a separate weighted component rather than blended into `form` so the breakdown shows both honestly. **Reliability gate**: below `MIN_MINUTES_FOR_XGI` (180 minutes, ~2 full games) a player's own `xgi90` is treated as neutral (50) and they're excluded from the pool used to compute `maxXgi90` — the per-90 stat is a real-data extrapolation that blows up at low sample sizes (a real case hit during development: a player with 1 minute played and a fluky 0.17 xGI contribution extrapolated to 15.3 per-90, which would have compressed every other player's normalized score toward zero had it been allowed to set the scale).
- **Availability multiplier (`availabilityMultiplier()`)**: `chance_of_playing_this_round`/`next_round` (0-100, `null` = no doubt = 100) is applied as a **multiplier on the final weighted score**, not as a 5th weighted-and-normalized component — it answers "how likely to deliver this score at all" rather than "how good if they play", so a 25% chance of playing quarters the whole score instead of being diluted into one nudge among several. Every scored player/candidate carries both `score` (post-multiplier) and `preAvailabilityScore` (what the 4 weighted components alone sum to) so the UI can show both instead of a breakdown that mysteriously doesn't add up to the final number.
- **Penalty order (`penaltyOrder`, from `penalties_order`)**: shown as an informational badge only (`PenaltyBadge` in `SuggestionsView.jsx`, first-choice takers only) — deliberately **not** weighted into the score, since how many penalties a team wins is too unpredictable to model as a formula input without implying false precision.

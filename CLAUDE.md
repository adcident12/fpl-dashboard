# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local FPL (Fantasy Premier League) decision-support dashboard. It reads only the public, unauthenticated FPL API — there is no login and no team automation. The user makes actual squad changes on the official FPL site themselves; this app just helps them decide what to do (player stats, fixture difficulty, squad view, transfer/captain suggestions).

The full spec lives in [.github/prompts/fpl-dashboard.prompt.md](.github/prompts/fpl-dashboard.prompt.md), written as 4 build phases (player table → fixture grid → my squad → transfer/captain suggestions). All 4 phases are implemented.

## Commands

Run from the repo root (`package.json` orchestrates both workspaces):

- `npm run install:all` — install server and client dependencies (they are separate npm packages, not a workspace/monorepo).
- `npm run dev` — run server (port 3001) and client (Vite dev server, port 5173) concurrently, with hot reload.
- `npm run build` — build the client only (`client/dist`).
- `npm start` — start the server only; if `client/dist` exists, the server serves it directly (single-process production mode).

There is no test suite and no linter configured in this repo.

To run just one side: `npm --prefix server start` or `npm --prefix client run dev`.

**Split deployment (GitHub Pages + Render):** GitHub Pages only serves static files, so `client/` and `server/` deploy separately — see `.github/workflows/deploy-pages.yml` and `render.yaml`. This is a second deployment mode alongside the single-process one above, not a replacement: `client/vite.config.js`'s `base` only switches to `/fpl-dashboard/` when the workflow sets `GITHUB_PAGES=true`, and `client/src/api.js`'s `API` constant only points at a remote backend when `VITE_API_BASE` is set at build time — both default to the original root-relative behavior otherwise, so `npm run build && npm start` locally is unaffected. Full setup steps (Render's free-tier cold-start/cache caveats included) are in the project's Obsidian doc, not duplicated here.

## Architecture

**Two independent npm packages, no shared code:**
- `server/` — Node.js (ESM) + Express. Fetches FPL API data, transforms/joins it, and serves JSON at `/api/*`.
- `client/` — React + Vite. Fetches from `/api/*` (proxied to `localhost:3001` in dev via `vite.config.js`).

**Server data flow (`server/fpl.js`):**
1. `getBootstrap()` / `getFixtures()` / `getElementSummary()` / `getEntryPicks()` / `getEventLive()` / `getEntryHistory()` — raw, disk-cached fetches from `https://fantasy.premierleague.com/api/*` (5 min TTL, see `server/cache.js`, backed by JSON files in `server/.cache/`).
2. `buildData()` — the core transform: joins `bootstrap-static` elements + teams + fixtures into a flat `players` array with computed fields (price in £m, parsed numeric strings, next-3-fixtures with FDR, differential). Nearly every other function builds on this. Its `meta` also carries `dataFetchedAt`/`dataTtlMs` (via `cache.js`'s `getCacheMeta()`, which reads a cache file's timestamp without affecting `getCached()`'s own fresh/stale logic) — the older of the `bootstrap`/`fixtures` cache timestamps, so the client can show a live "Updated Xm ago" indicator (`App.jsx`, header, ticks every 30s). `meta.nextDeadline` (`{ eventId, eventName, deadlineTime, deadlineEpochMs }`) is the next gameweek deadline that hasn't passed yet — found by scanning `bootstrap.events` for the first `deadline_time` after "now" directly, rather than trusting the `is_next` flag, which can lag right around a deadline; the header renders it as a live countdown (same 30s tick as freshness) that turns amber under 24h and red under 3h.
3. `buildFixtureGrid()` — teams × next-5-gameweeks matrix for the fixture difficulty view. Each cell is an **array** of fixtures, not a single fixture-or-null — 0 fixtures means a Blank Gameweek (BGW), 2+ means a Double Gameweek (DGW), both real occurrences during a season when the schedule reshuffles postponed matches. It also returns `doubles`/`blanks` summary arrays (`{ teamId, teamShort, event, count? }`) computed in the same pass, which the client (`FixtureGrid.jsx`) renders as a banner above the grid grouped by gameweek.
4. `buildSquad(teamId, eventId)` — joins a user's picks (`entry/{id}/event/{gw}/picks`, plus `event/{gw}/live/` for each pick's live points) against `buildData()`'s player list. Starting XI vs bench is derived from `pick.position <= 11` — the picks API has no `starting` boolean.
5. `buildTransferSuggestions()` / `buildCaptainSuggestions()` / `buildSquadScan()` — the scoring engine (see below), built on `getSquadContext()` which combines squad picks + bank (read directly from `entry_history.bank`, not derived) + the full player pool, **plus `eventFixturesByTeam`**: every team's actual fixture(s) for the specific gameweek being planned for (`ctx.ev`), read straight from `getFixtures()` rather than from `buildData()`'s `nextFixtures` (which lists the next 3 *real matches* chronologically and so silently skips a Blank Gameweek, and can't tell a Double Gameweek's two legs apart from two fixtures spread across different future gameweeks). `eventFixturesFor(ctx, teamId)` reads it — 0 entries = blank, 2 = double — and both `scoreTransferComponents()` and `buildCaptainSuggestions()` use it to correct the score: a blank forces the fixture component to **0** (not the neutral-midpoint fallback used for genuinely missing data — a blank is a guaranteed zero, not an unknown), a double adds `SCORING.dgwBonus` (+20) for the extra scoring chance. Every scored player/candidate carries `eventFixtureCount`/`blankEvent`/`dgwEvent`, and `breakdown.fixture.note` (`'blank'`/`'double'`/`null`) says which adjustment fired — surfaced in the UI as a BLANK/DGW×2 badge next to the name (`SuggestionsView.jsx`'s `EventFlagBadge`) so the adjustment is never a silent number shift. `buildSquadScan()` runs the same per-player logic as `buildTransferSuggestions()` (factored into `scoreAffordableCandidates()`/`scoreTransferComponents()`) across all 11 starting players at once, comparing each to its top same-position replacement — one swap at a time, not a combined-budget multi-swap optimization.
6. `buildBonusPredictor(eventId)` — fan feature, league-wide (no team ID needed): projects live bonus points (3/2/1) per fixture from each player's current `bps` (Bonus Points System score, from `event/{gw}/live/`), using `computeBonusPoints()` — FPL's own tie-break rule (rank by BPS descending, group players tied on the exact value, award the group's *starting* rank's points to every member, then advance the running rank by the group's size, not by 1 — reproduces FPL's real "2 tied for 1st both get 3, next distinct player gets 1, '2nd' is skipped" behavior). Grouped per fixture (each player's fixture read from `explain[0].fixture`, not assumed from their team's single fixture that event) so bonus is never compared across different matches; only fixtures with `started === true` are included. Uses a 60-second cache (`LIVE_BONUS_TTL_MS`, passed as `getEventLive(eventId, ttlMs)`'s 2nd arg) instead of the app-wide 5 minutes, since BPS changes minute to minute during play — `getCached()`'s TTL is a per-call read-time check against the cache file's own timestamp, not something stored with the file, so this doesn't affect `buildSquad()`'s own (default-TTL) reads of the same cached data. A fixture's `finished` flag is `f.finished || f.finished_provisional` (same quirk as `buildFixtureGrid()`'s `done`) — a fully-played match can sit at `finished=false` for up to ~1h while FPL's own bonus confirmation catches up, and `finished_provisional` (plus the score already being posted) is the earlier, reliable signal that the match is actually over and `confirmedBonus` (`stats.bonus`) is authoritative.
7. `buildChipPlan(teamId, eventId)` — chip planning helper. `bootstrap.chips[]` (8 entries: 4 chip types × 2 season halves, each `{ name, start_event, stop_event }`) is the **authoritative source for chip windows** — never hardcode the GW19 half-boundary, read it from here. `entry/{id}/history/`'s own `chips[]` (`{ name, event, time }`) is the user's actual usage, matched to a window by `name` + `event` falling inside that window's range — so, unlike the original feature-roadmap note assumed, **no manual "which chips have I used" input is needed**. Each returned window carries a single `status` (`used`/`available`/`expiringSoon`/`upcoming`/`expired`) the client switches on directly. `recommendations[]` are heuristic, one per chip type, only computed when that chip is currently available: Bench Boost when all 4 bench players have an easy next fixture and are expected to play; Triple Captain when the top captain-formula pick also has an easy next fixture; Free Hit when 2+ of the user's own squad's teams have a blank in the very next gameweek (reuses `buildFixtureGrid()`'s `blanks`); Wildcard when 4+ starting XI are flagged `upgrade` by `buildSquadScan()` (squad needs a broad rebuild, not a single swap).

Routes in `server/index.js` are thin wrappers around these functions; there's no separate route/controller/model layering.

**OpenAPI/Swagger (`server/openapi.js`):** a hand-written OpenAPI 3.0 document (validated with `@apidevtools/swagger-parser`, not just "renders in Swagger UI without erroring") covering all 14 routes — **not** generated from JSDoc comments on the routes themselves (`swagger-jsdoc`), because this API's response shapes are deeply nested and quirky enough that inline comment blocks would drift silently; the schemas here are typed from the same verified field knowledge as `fpl-api-quirks.instructions.md`/`fpl-scoring.instructions.md`. Served at `/api-docs` (Swagger UI) and `/api-docs.json` (raw spec — CORS is already open, so external tooling can fetch it directly; built specifically so an OpenAPI→MCP bridge can consume it). **When a route's request/response shape changes, update the matching schema in `openapi.js` in the same commit** — same discipline as the API quirks doc, and worth being strict about here since a wrong schema silently breaks whatever consumes the spec, not just a doc reader.

**Client structure (`client/src`):** `App.jsx` owns the player table + tab navigation and fetches via `api.js`; `FixtureGrid.jsx`, `SquadView.jsx`, `SuggestionsView.jsx`, `ChipsView.jsx`, `BonusView.jsx`, `GuideView.jsx` are the other six tabs, each fetching its own data independently (no global state/store, except language — see below). `ChipsView.jsx` renders `buildChipPlan()`'s 8 windows as two half-of-season columns of status cards (color/label driven by each window's `status`) plus a recommendations list; like `SquadView`/`SuggestionsView` it needs a Team ID, so it reuses `useTeamId()`/`TeamIdInput`/`TeamIdEmptyState`. `BonusView.jsx` is the one tab that needs **no Team ID** (league-wide fan data, not squad-specific) — it renders `buildBonusPredictor()`'s per-fixture cards (BPS-sorted player list, gold/silver/bronze 3/2/1 bonus badges) and re-polls every 60s (`REFRESH_MS`, matching the server's own `LIVE_BONUS_TTL_MS` so a faster client poll wouldn't just re-read the same cached response) for as long as the tab stays mounted; a fixture's badge tooltip and "LIVE"/"FINAL" tag text differ depending on `finished` (projection vs FPL's own confirmed bonus). `GuideView.jsx` is the one tab with **no data fetching at all** — a static, hand-written explainer of the scoring formula and every badge used elsewhere in the app (reusing the exact same CSS classes as live badge previews, not a text description), added because badge/score tooltips rely on `title` attributes that don't work on touch devices; its EN/TH content lives directly in the component as two JSX blocks switched on `useLang()`'s `lang`, **not** through `i18n.jsx`'s `STRINGS` dictionary — that dictionary is for short UI labels, and per-sentence keys for paragraph-length prose would be unwieldy. `PitchView.jsx` is a shared formation-view component (GK/DEF/MID/FWD rows sized to the squad's actual formation, bench below, team-colored jersey chips — no image assets) used by both `SquadView` and `SuggestionsView`'s squad-scan section; given `buildSquadScan()`'s rows, it numbers starting players flagged `upgrade` by transfer-priority (biggest score gap first). Its `mode` prop (`'current'` default, or `'suggested'`) toggles between the real squad and a hypothetical one where every `upgrade`-flagged starter is swapped for its top scan candidate (dashed-outline chips) — `SuggestionsView` exposes this as a "current team / suggested team" toggle above the pitch. `FdrBadges.jsx` is the shared fixture-difficulty badge row (opponent + color-coded FDR, used by the Players table, My Squad, and every Suggestions candidate list) — every server-side suggestion object (transfer candidates, captain candidates, squad-scan `suggestion`) carries a `nextFixtures` array in the same shape as `buildData()`'s players specifically so this one component can render all of them.

**Localization (`i18n.jsx`):** EN/TH UI strings live in one `STRINGS` dictionary keyed by dotted names (e.g. `table.player`); `LangProvider` (wraps `<App>` in `main.jsx`) is the **one deliberate exception** to "no global state" — it's a React Context holding `{ lang, setLang, t }`, needed because the language toggle in `App.jsx`'s header must stay in sync across every tab, several levels deeper than prop-drilling would reach cleanly (`SuggestionsView` → `PitchView`/`FdrBadges`/`ScanRow`/`CandidateRow`). `useLang()` reads it; language persists to `localStorage` (`fpl-lang`, default `'en'`) the same way `useTeamId()` persists the team ID. **Only UI chrome is translated** — player/team/opponent names and other FPL API data are never translated, and technical fallback error strings in `api.js` (e.g. "Failed to load squad (500)") intentionally stay in English, matching how raw server error messages are already shown as pass-through text elsewhere. Adding a string: add both `en`/`th` entries to `STRINGS` in `i18n.jsx`, then reference via `t('your.key')` (or `t('your.key', { var })` for `{{var}}` interpolation).

**Styling — Tailwind CSS v4 + a slimmed-down `styles.css`, deliberately hybrid, not "all Tailwind":** `@tailwindcss/vite` is wired into `vite.config.js`; `styles.css` opens with `@import "tailwindcss";` then an `@theme` block mapping the app's design tokens (`--color-bg/panel/panel-2/panel-3/text/muted/line/accent/accent-2/easy/med/hard`, `--radius-sm/md/lg/xl`, `--font-display`/`--font-body`) into Tailwind's namespace, so `bg-panel`, `text-accent`, `rounded-md`, `font-display` etc. all resolve to *this app's* values, not Tailwind's defaults. `--transition: 200ms cubic-bezier(0.2, 0, 0, 1)` (Material 3's "emphasized" easing) stays a plain custom property (referenced by the hand-written CSS below; Tailwind has no matching utility). `--font-display` is Rajdhani, loaded via Google Fonts in `index.html`, used only for headings/tabs/section labels — data-dense tables stay on `--font-body` for legibility.

**Visual language — Material Design 3, dark theme (2026-09-05 redesign):** the `--radius-*` scale and `--color-panel-3` (a third, lighter surface tone — MD3's "surface-container-highest") exist specifically to support this. Cards/panels/tables get `shadow-sm` (Tailwind's default shadow scale, used as-is — no custom elevation tokens; it's dark-theme-appropriate without tuning) via className, not the hand-written classes, wherever the surface is one already styled with Tailwind utilities; **filled buttons are pill-shaped** (`rounded-full` + `shadow-sm`, brightening/`shadow-md` on hover) and **outlined buttons stay flat** (no shadow) — this mirrors MD3's Filled vs Outlined button elevation rule. Small status badges/chips (`.pos`, `.fdr-badge`, `.badge`) are pill-shaped (`border-radius: 9999px`); breakdown chips (`.chip` in `SuggestionsView.jsx`) use `--radius-sm` (8px, MD3's chip corner radius) and `--color-panel-3` so they read as one tone lighter than the `.breakdown-row` they sit on, not blended into it. **`PitchView.jsx`'s `.jersey` uses `filter: drop-shadow(...)`, never `box-shadow`** — `box-shadow` follows an element's rectangular box, not its `clip-path`-cut silhouette, so it would draw a shadow rectangle around the jersey's invisible bounding box instead of hugging its shape; `filter: drop-shadow()` operates on the actual rendered (clipped) pixels and is the only shadow safe to use there.

**Tooltips (`Tooltip.jsx`):** replaces `title=` attributes app-wide (badges, breakdown chips, FDR badges, captain/vice-captain/news flags, the header's deadline/freshness indicators, `FixtureGrid.jsx`'s cells) because `title=` never fires on tap on a touch device — there is no hover on a phone, so every one of these was previously invisible to mobile users (the Guide tab's badge glossary was a first, page-level fix for this same gap; `Tooltip.jsx` is the per-badge fix). Hover+focus opens it on desktop; a single tap toggles it on a touch device (detected once, globally, via a one-time `touchstart` listener). Positioned with `@floating-ui/dom` (`computePosition`/`autoUpdate`/`offset`/`flip`/`shift`) and rendered through a `createPortal` into `document.body` with `position: fixed` — **not** positioned inline where the trigger sits — so it can never be clipped by an ancestor's `overflow: auto` (several triggers live inside a `.table-wrap` scroll container; an inline-positioned tooltip would get cut off there the same way a badge inside `PitchView`'s clip-path jersey used to before that was fixed), and so its look (Material-styled: rounded, bordered, themed) is fully controllable — unlike a native browser tooltip, which ignores CSS entirely and is positioned by the browser/OS, not the page (a real, user-reported inconsistency next to every other tooltip in the app once `FixtureGrid.jsx` was the one place still on native `title=`). Visual style is MD3's "plain tooltip" (small, no arrow — arrows are only on MD3 "rich" tooltips). `Tooltip`'s `as` prop (`'span'` default, `'div'` for `FixtureGrid.jsx`) picks the trigger wrapper's tag so a block-level trigger (`.cell`, a flex container) doesn't end up nested inside an inline `<span>`. **Two deliberate exceptions kept on native `title=`:** `TeamIdControls.jsx`'s "Try sample team" button (wrapping an actionable button in `Tooltip`'s tap-to-toggle handler would fire both the tooltip toggle and the button's own `onClick` on the same tap — a real conflict, not just a missed nice-to-have, so the button's own visible label carries the affordance instead); and `PitchView.jsx`'s jersey badges (explicitly commented in-file — same "Claude can't visually verify, and this exact area already had real layout bugs" reasoning the Tailwind exemption below already uses, applied to the tooltip mechanism specifically; `FixtureGrid.jsx` was under the same exemption until a user screenshot showed the native-tooltip inconsistency was worse than the theoretical risk, so it was switched over).

**Loading states (`LoadingSpinner.jsx`):** every "nothing to show yet" screen (initial load in `App`/`FixtureGrid`/`SquadView`/`SuggestionsView`, the Quick Squad Scan and Captain sections while scoring) uses the same `LoadingState` (centered ring spinner + label) or bare `Spinner` (dropped into a loading button, e.g. `TeamIdInput`'s Load button) — both are Tailwind's own `animate-spin` under `motion-safe:`, no custom CSS/keyframes. Before this, `SquadView` and `SuggestionsView`'s initial team load showed nothing at all while waiting (not just plain text) — a real gap, not merely unstyled. When adding a new loading state, reach for one of these two instead of ad hoc text so every wait in the app reads the same way.

Most components (`App.jsx`, `TeamIdControls.jsx`, `SquadView.jsx`, `SuggestionsView.jsx`) are styled with Tailwind utility classes directly in JSX, including responsive variants (`max-sm:`, `max-[900px]:` — Tailwind's `sm` breakpoint is exactly 640px, which is why this app's two breakpoints line up with `sm`/a custom `900px` value). **What deliberately stays as hand-written CSS in `styles.css`, and why:**
- **Classes built from a runtime value** (`` `pos-${positionId}` ``, `` `fdr-${bucket}` ``, `` `badge verdict-${verdict}` ``, `` `jersey-chip${isSuggested ? ' suggested' : ''}` ``, `` `chip-status-${w.status}` `` in `ChipsView.jsx`): Tailwind's compiler statically scans source files for complete class-name strings — it cannot see `pos-${positionId}` and so cannot generate CSS for it. These variant/color-coding families (`.pos-1..4`, `.fdr-easy/med/hard`, `.badge.verdict-*`, `.top-pick`, `.bench`, `.chip-status-*`) are small hand-written classes for exactly this reason, matched in JSX via the same template-literal pattern.
- **The responsive card-table technique** (`table.players` and its variants across Players/My Squad/Suggestions — see below): the `data-label` + `::before { content: attr(data-label) }` mechanism, `<thead>`-hiding, and the dynamic `.name:not([data-label])` title rule are structural CSS that doesn't map cleanly to inline utilities and is shared identically across four different tables.
- **`PitchView.jsx`'s jersey/pitch mechanics**: the jersey silhouette (`clip-path: polygon(...)`), the pitch gradient, and the badge-positioning fix (badges must be siblings of `.jersey`, not children, because `clip-path` clips descendants — see the comment in `PitchView.jsx`) are effect-heavy and already fragile (two real bugs were found and fixed here); the structural mechanics stay untouched on that history alone — a `chrome-devtools-mcp` browser became available partway through this project (2026-09-05) and confirmed the jersey rendering is correct as of the Material redesign, but that doesn't retroactively make restructuring this area risk-free, so the same caution still applies to *changes*, just no longer to *verification*.
- **`FixtureGrid.jsx`** (the teams×gameweeks matrix) is exempt from the whole Tailwind pass for the same reason it's exempt from the card-table treatment (see Responsive below) — kept as-is.
- Team-color hashing (`teamColor()` in `PitchView.jsx`) sets an inline `style`, not a class, so it was never a Tailwind concern.

When adding new UI: reach for Tailwind utilities first; only add a hand-written class in `styles.css` if it needs a runtime-constructed class name, overrides native-control pseudo-elements (like the custom `<select>` arrow or the checkbox-as-toggle-switch — both still hand-written for exactly this reason), or is part of the card-table/jersey systems above.

**Responsive:** two breakpoints at the end of `styles.css`, `900px` (tightens spacing, shrinks `PitchView` jersey chips) and `640px` (stacks every control bar full-width, shrinks the pitch further, and turns every `table.players`-based table — Players/My Squad/Suggestions — into one card per row via a CSS-only technique: `<thead>` hidden, each `<td>` becomes a flex row labeled by its `data-label` attribute's `::before` content, and `td.name:not([data-label])` renders as the card's title instead of a labeled field). Every `<td>` that needs a mobile label carries `data-label={t('...')}` in the JSX — a `<td>` with no `data-label` and no `.name` class (e.g. `colspan` divider/breakdown rows) just renders as a plain block. **`table.fixture-grid` (FixtureGrid.jsx) is deliberately exempt** from the card treatment — it's a teams×gameweeks matrix, not a list of records, and stacking it would defeat comparing several gameweeks side by side; it only scrolls horizontally with tighter cell sizing at 640px.

**Mobile primary navigation — fixed bottom tab bar (2026-09-05, Facebook-mobile-style):** `App.jsx`'s top pill nav (`hidden sm:inline-flex` — visible ≥640px) and a second `<nav>` right below the header (`hidden max-sm:flex fixed bottom-0 inset-x-0` — visible <640px only) render the *same* `TABS` array, so there's exactly one source of truth for the tab list; both read/write the same `tab` state, so switching via either stays in sync. This exists because the original single top nav had **no width constraint of its own** — the tab buttons in one `inline-flex` row just grew the whole page wider than the viewport on a phone instead of wrapping, silently making some tabs unreachable; this was found (and the whole redesign visually verified, screenshot by screenshot, for the first time this session) once real browser tooling became available, not by inspecting the CSS. `Icons.jsx` has one small hand-drawn line-icon SVG per tab (no icon library — a handful of glyphs isn't worth the dependency) rendered at `w-5 h-5` in the bar, colored via `currentColor` so the active/inactive text-color classes drive the icon too. The bottom bar has `style={{ paddingBottom: 'env(safe-area-inset-bottom)' }}` for notched phones, and the app's outer wrapper gets `max-sm:pb-20` so the bar never permanently covers the last bit of page content (it still covers content transiently while scrolling past that screen position, same as any fixed bottom bar — Instagram/Facebook do this too, it's not a bug). The header's own mobile row had a second real bug found the same way: the deadline badge had no `whitespace-nowrap`, so on a narrow screen its own text wrapped to two lines inside the pill and visually broke apart — every header pill/button now carries `whitespace-nowrap` for exactly this reason, and the verbose "Gameweek 3 · 652 players" text hides on mobile (`max-sm:hidden`) in favor of just the freshness dot + deadline badge, decluttering the top bar the way a minimal mobile app header does.

## FPL API field quirks — read before touching data mapping

The public FPL API is undocumented and has non-obvious field names/shapes. **Full verified mapping: [.github/instructions/fpl-api-quirks.instructions.md](.github/instructions/fpl-api-quirks.instructions.md).** Do not guess field names — check that file first, and add any newly-discovered quirk to it. Key traps:

- Players are under `elements`, not `players`.
- `element_type` is a position **ID** (1=GK, 2=DEF, 3=MID, 4=FWD), not a string — map via `element_types`.
- `now_cost` is in tenths of £m (`60` = £6.0m).
- Many stats (`form`, `selected_by_percent`, `value_season`, `ict_index`, `expected_goals`, etc.) are **strings**, not numbers — must be parsed.
- FDR is per-team-per-fixture: `team_h_difficulty` / `team_a_difficulty` (1-5 scale, 1=easiest), not a single `difficulty` field.

## Scoring engine

Transfer and captain suggestions use one transparent, reproducible formula — **never a black-box ranking; always return the per-component breakdown** (raw value, normalized 0-100 value, weight, weighted points). Full spec: [.github/instructions/fpl-scoring.instructions.md](.github/instructions/fpl-scoring.instructions.md).

- All weights live in the single `SCORING` config object in [server/fpl.js](server/fpl.js) — tune there, not inline.
- Every component is normalized to 0-100 before weighting; a missing/null component falls back to the neutral midpoint (50), never to zero — **except the fixture component on a confirmed Blank Gameweek**, which is forced to 0 (see below): that's a known guaranteed zero, not missing data, so the neutral-midpoint fallback would be wrong there.
- FDR normalization is `(5 - avgFDR) / 4 * 100` (1=easiest→100, 5=hardest→0). Note the code comment in `fpl.js` explaining why this differs from the prompt file's original (buggy) `(6 - avgFDR)/4*100` formula — the `(5 - x)/4` form is the corrected, actually-0-100-bounded version.
- Transfer scoring weights next-3-gameweek average FDR; captain scoring weights the actual fixture(s) of the specific gameweek being planned for (not "whichever real match comes next chronologically" — see `buildCaptainSuggestions()` above) and only considers the starting XI.
- **Double/Blank Gameweek correction**: both transfer and captain scoring adjust the fixture component using `eventFixturesFor(ctx, teamId)`'s count for the target gameweek — 0 forces it to 0, 2+ adds `SCORING.dgwBonus`. This is layered on top of the normal FDR normalization above, not a replacement for it.
- **4th component — `underlying` (xG+xA per 90, `normUnderlying()`)**: added alongside form/fixture/value (weights rebalanced — see `SCORING`) because `form` is backward-looking actual points (mixed with finishing luck) while xGI is forward-looking "should be scoring this much"; kept as a separate weighted component rather than blended into `form` so the breakdown shows both honestly. **Reliability gate**: below `MIN_MINUTES_FOR_XGI` (180 minutes, ~2 full games) a player's own `xgi90` is treated as neutral (50) and they're excluded from the pool used to compute `maxXgi90` — the per-90 stat is a real-data extrapolation that blows up at low sample sizes (a real case hit during development: a player with 1 minute played and a fluky 0.17 xGI contribution extrapolated to 15.3 per-90, which would have compressed every other player's normalized score toward zero had it been allowed to set the scale).
- **Availability multiplier (`availabilityMultiplier()`)**: `chance_of_playing_this_round`/`next_round` (0-100, `null` = no doubt = 100) is applied as a **multiplier on the final weighted score**, not as a 5th weighted-and-normalized component — it answers "how likely to deliver this score at all" rather than "how good if they play", so a 25% chance of playing quarters the whole score instead of being diluted into one nudge among several. Every scored player/candidate carries both `score` (post-multiplier) and `preAvailabilityScore` (what the 4 weighted components alone sum to) so the UI can show both instead of a breakdown that mysteriously doesn't add up to the final number.
- **Penalty order (`penaltyOrder`, from `penalties_order`)**: shown as an informational badge only (`PenaltyBadge` in `SuggestionsView.jsx`, first-choice takers only) — deliberately **not** weighted into the score, since how many penalties a team wins is too unpredictable to model as a formula input without implying false precision.
